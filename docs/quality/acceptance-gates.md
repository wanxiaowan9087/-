# 验收门与质量治理

## 1. 目的与适用范围

本文定义本项目唯一、可重复、可审计的交付验收方式。它适用于本地验收、CI、合并判断和演示候选版本，不替代 API 契约、架构设计或各子 Agent 的职责说明。

除非本文明确标记为“仅记录”，所有使用“必须”“不得”的条目都是阻断门。任一阻断门失败时，不得宣称完成、允许合并或请求远程推送。

## 2. 唯一验收入口

### 2.1 权威命令

项目完成工程化脚手架后，必须提供以下唯一的完整验收入口：

```bash
python scripts/quality_gate.py all --integration-sha <40位Git提交SHA>
```

`scripts/quality_gate.py` 是质量编排器，不得在其中重新实现测试逻辑。它只能调用各模块原生 lint、类型检查、测试、评测和冒烟命令，汇总退出码，并生成机器可读报告。

在该脚本尚未实现前，项目不满足验收条件。README、CI 和交付报告必须引用上述命令，不得再定义第二套“完整验收”命令。

### 2.2 子命令

允许为开发反馈提供以下子命令，但子命令通过不代表项目验收通过：

```bash
python scripts/quality_gate.py contract
python scripts/quality_gate.py apifox
python scripts/quality_gate.py backend
python scripts/quality_gate.py agent
python scripts/quality_gate.py rag
python scripts/quality_gate.py frontend
python scripts/quality_gate.py e2e
python scripts/quality_gate.py compose
python scripts/quality_gate.py security
```

`all` 必须在干净环境中按依赖关系执行全部子命令，不得因本地已有缓存、已启动服务或缺少可选依赖而静默跳过。允许并行执行互不依赖的子命令。

### 2.3 统一行为

质量编排器必须满足：

- 成功退出码为 `0`；任一阻断项失败、跳过、超时或报告缺失时退出码非 `0`。
- 验证当前 `HEAD` 与 `--integration-sha` 完全一致，且 SHA 必须是 40 位不可变提交标识。
- 记录操作系统、Python、Node、浏览器、Docker、数据库迁移版本、测试数据版本、RAG 基线版本和开始/结束时间。
- 默认使用 Fake Model 和固定 Embedding；不得访问付费模型或依赖非固定的在线响应。
- 生成 `artifacts/quality/acceptance-report.json` 和便于阅读的同名 Markdown 报告。
- 报告至少包含 SHA、每个子命令的实际命令、退出码、用时、通过/失败/跳过数量及失败摘要。
- 不得使用任意延长等待、自动重跑整个失败套件或修改快照来制造通过；允许的重试必须是被测业务规则本身的一部分。

## 3. CI 作业

CI 中所有质量作业必须检出同一个提交 SHA，并使用锁定依赖。建议作业名固定如下：

| CI job | 调用 | 阻断条件 |
|---|---|---|
| `quality-contract` | `quality_gate.py contract` | OpenAPI、Pydantic、普通响应或流式事件契约不一致 |
| `quality-api-scenarios` | `quality_gate.py apifox` | Apifox CLI 场景、断言、数据驱动用例或报告生成失败 |
| `quality-backend` | `quality_gate.py backend` | lint、类型检查、单元、Repository、事务或迁移测试失败 |
| `quality-agent` | `quality_gate.py agent` | 工具、重试、超时、取消、降级、审核触发或记忆测试失败 |
| `quality-rag` | `quality_gate.py rag` | 固定评测集缺失、硬阈值未达标或发生禁止回归 |
| `quality-frontend` | `quality_gate.py frontend` | lint、类型检查、组件、状态或无障碍测试失败 |
| `quality-security` | `quality_gate.py security` | 密钥、隐私数据、危险日志或高危依赖/镜像问题 |
| `quality-e2e` | `quality_gate.py e2e` | 真实前后端联调场景失败 |
| `quality-compose` | `quality_gate.py compose` | 全新环境构建、启动、迁移、健康检查或关闭失败 |
| `acceptance-all` | `quality_gate.py all --integration-sha "$CI_COMMIT_SHA"` | 任一完整验收项失败或缺失 |

`acceptance-all` 是权威合并门，必须依赖前述快速反馈作业全部成功。即使各子作业已经通过，它仍须针对最终候选 SHA 执行总入口；不得只汇总来自不同 SHA 的旧报告。

CI 必须保存验收报告、JUnit 报告、前端覆盖率、Playwright trace/截图、RAG 指标与 Compose 日志。失败日志在上传前必须执行密钥和隐私数据脱敏。

## 4. 必过测试矩阵

下表中每一行都是阻断项。测试数量可以增加，不得在没有审批的情况下删除或降级。

| 域 | 必过场景 | 主要层级 | 默认依赖 |
|---|---|---|---|
| API 契约 | 每个冻结接口的请求、成功响应、错误响应、HTTP 状态码和 `request_id` | 契约/集成 | FastAPI 测试客户端 |
| API 黑盒场景 | Apifox CLI 覆盖会话生命周期、分页、幂等重放/冲突、取消、反馈、记忆和审核权限；生成 JSON 与 JUnit 报告 | 场景/集成 | 真实 FastAPI + Apifox CLI |
| 流式契约 | `meta`、`status`、工具、`delta`、引用、审核、`done`、`error` 的 payload、顺序与终止规则 | 契约/集成 | Fake Model |
| 会话 | 创建、读取、消息历史、恢复、空会话、未知 ID、并发更新 | 集成/E2E | PostgreSQL |
| Agent 工具 | 成功、参数错误、失败、超时、有上限重试、取消、降级和结果脱敏 | 单元/集成 | Fake Tool Adapter |
| 持久化 | Repository、事务提交/回滚、连接关闭、Redis 非唯一数据源 | 集成 | 临时 PostgreSQL/Redis |
| 迁移 | 空库升级到最新、已有数据升级、降级或明确的恢复方案、重复执行 | 集成/Compose | Alembic |
| RAG | 分片元数据、向量与关键词检索、融合、重排、引用、拒答和版本更新 | 单元/评测 | 固定 Embedding |
| 记忆 | 来源、置信度、创建、纠正、停用、删除及提取失败不阻塞回答 | 单元/集成/E2E | Fake Model |
| 人工审核 | 全部触发规则、批准、驳回、编辑后发布、重复决定、并发冲突和审计记录 | 单元/集成/E2E | Fake Model |
| 前端 | 会话、流式拼接、取消、重试、工具状态、引用、审核、加载/空/错误/禁用状态 | 组件/集成 | Mock 协议层 |
| 无障碍 | 键盘完成核心流程、可见焦点、语义名称、对比度和常用视口响应式 | 组件/E2E | 自动扫描加关键手工清单 |
| 真实联调 | 浏览器连接真实 FastAPI、PostgreSQL、Redis 和 Chroma；只允许模型与 Embedding 为 Fake | Playwright E2E | Docker Compose |
| 失败路径 | 模型、工具、检索、存储不可用，SSE 中断，重复请求及服务重启 | 集成/E2E | 可控故障注入 |
| Compose | `docker compose up --build`、就绪检查、迁移、基本对话、优雅关闭 | 冒烟 | 全新 Docker 环境 |
| 安全 | 提交历史外的当前树密钥扫描、日志/响应泄露、Prompt 注入、越权审核和依赖高危项 | 静态/集成 | 固定规则库 |

不得仅用 Mock HTTP 响应替代“真实联调”。真实联调要求浏览器发出真实网络请求，并由运行中的 FastAPI 和真实基础设施 Adapter 处理；Fake Model 与固定 Embedding 不影响这一判定。

Apifox CLI 是 `all` 的阻断组成，不是第二套完整验收入口。其场景和非敏感数据保存在 `tests/apifox/`；CI 报告写入 `artifacts/apifox/` 并汇总到总验收报告。具体边界、运行模式和密钥规则见 `docs/testing/apifox-cli.md`。

## 5. RAG 验收阈值

### 5.1 固定评测集

默认评测集为 25 条，允许在 25 至 30 条范围内扩充，但必须至少包含：

- 12 条可直接命中单一来源的问题；
- 4 条需要多个来源或融合检索的问题；
- 4 条无依据、应拒答的问题；
- 3 条相似型号、冲突来源或易混淆问题；
- 2 条 Prompt 注入或与问题无关的检索内容。

每条样本必须有稳定的 `case_id`、问题、是否应回答、期望 `document_id/chunk_id` 集合、禁止来源、标签和修改理由。不得只保存自然语言“参考答案”而缺少来源标签。

### 5.2 实习项目默认硬阈值

以下阈值使用固定语料、固定分片配置、固定 Embedding 和同一评测版本计算：

| 指标 | 定义 | 硬阈值 |
|---|---|---|
| `retrieval_hit_rate@5` | 可回答样本的 Top-5 中至少出现一个期望分片 | `>= 0.80` |
| `mrr@10` | 第一个期望分片倒数排名的平均值 | `>= 0.65` |
| `ndcg@10` | 按标注相关性计算的排序质量 | `>= 0.70` |
| `citation_integrity` | 返回的引用 ID 均存在、版本匹配且可定位 | `= 1.00` |
| `citation_support_precision` | 引用实际支持对应结论的比例 | `>= 0.90` |
| `unanswerable_refusal_recall` | 应拒答样本中正确拒答的比例 | `>= 0.90` |
| `answerable_false_refusal_rate` | 可回答样本被错误拒答的比例 | `<= 0.10` |
| `prompt_injection_defense_rate` | 注入样本中未服从检索指令且未泄露内部信息的比例 | `= 1.00` |

小样本比例必须同时报告分子和分母。指标恰好位于阈值时视为通过。延迟、Token 数和成本默认只记录不阻断；当 CI 环境固定后，可以通过审批增加性能硬门。

### 5.3 回归与基线更新

除满足硬阈值外，候选版本相对已批准基线还必须满足：

- `retrieval_hit_rate@5`、`mrr@10`、`ndcg@10`、`citation_support_precision` 任一指标不得下降超过 `0.03` 绝对值。
- `citation_integrity` 和 `prompt_injection_defense_rate` 不得下降。
- 不得删除失败样本、放宽标签或改变语料来掩盖实现回归。

只有以下情况允许更新基线：语料有意变更、评测标注经复核纠错、分片/检索目标发生已批准的设计变化，或新增了代表性样本。基线更新必须：

1. 保留旧基线，不得覆盖历史文件；
2. 同时提交变更原因、样本差异、旧/新完整指标和逐样本差异；
3. 由 AI/RAG 工程师提出、QA 独立复核、根 Agent 确认；
4. 新基线仍满足所有硬阈值；
5. 降低硬阈值、删除安全样本或改变“应回答/应拒答”语义时，必须取得用户审批。

满足第 1 至 4 项的普通基线更新属于内部质量签核，不属于第 7 节的视觉、API 或 Git 推送用户审批；但必须在基线变更记录中保留提出人、复核人、确认人、时间和差异引用。触发第 5 项时，内部签核不能替代用户审批。

## 6. 最终集成 SHA 全量回归

最终候选版本必须以集成分支上的 40 位提交 SHA 标识。QA 在开始验收前记录：

- 仓库与集成分支；
- 最终集成 SHA；
- 被合并的各角色分支 SHA；
- 契约版本、数据库迁移版本、评测集版本；
- Compose 配置摘要和镜像摘要；
- 是否存在未提交文件。

QA 必须在该 SHA 的干净检出上执行唯一验收命令。测试过程中不得修改候选源码、契约、快照、评测标签或基线。

以下任一事件会使验收结论立即失效并要求对新 SHA 重跑 `all`：

- 候选分支产生新提交、变基、合并或 cherry-pick；
- 依赖锁文件、迁移、Compose、Prompt、语料、评测集或配置发生变化；
- 为修复测试环境而修改仓库文件；
- 实际构建镜像不再对应记录的 SHA。

只有 `acceptance-report.json` 的 SHA 与候选 SHA 一致、全部阻断项通过、无跳过项且 QA 输出“允许合并”时，才允许合并。合并提交若改变了树内容，必须对合并提交再次执行总入口。

## 7. 审批证据

本节规定的视觉、API、架构、破坏性数据和 Git 推送审批必须来自用户的明确肯定表达；沉默、超时、历史上的泛化授权或子 Agent 推断均不算批准。证据可以保存在任务记录或仓库治理记录中，但必须提供稳定引用。RAG 普通基线更新按第 5.3 节执行内部质量签核；只有该节明确列出的治理变更才升级为用户审批。

所有审批记录至少包含：

| 字段 | 含义 |
|---|---|
| `approval_id` | 唯一标识 |
| `approval_type` | `visual`、`api`、`architecture`、`destructive_data` 或 `git_push` |
| `requested_by` | 请求人/Agent |
| `approved_by` | 实际用户标识 |
| `requested_at` / `decided_at` | 带时区 ISO 8601 时间 |
| `decision` | `approved` 或 `rejected` |
| `scope` | 本次批准的准确范围 |
| `artifact_ref` | 可稳定定位的稿件、契约 diff 或提交引用 |
| `conditions` | 用户附加条件；无则为空列表 |
| `evidence_ref` | 原始批准消息或记录的稳定引用 |

### 7.1 视觉审批

额外证据字段：

- 静态稿版本或内容摘要；
- 桌面与移动端截图引用；
- 主题、字体、颜色、布局和核心组件清单；
- 已知未实现交互及 Mock 数据说明。

出现以下任一情况必须重新审批：

- 品牌色、字体、视觉密度、主导航或页面信息架构实质变化；
- 对话区、引用卡片、运行追踪或人工审核的核心布局变化；
- 新增此前未展示的主页面或移动端布局发生实质变化；
- 批准的静态稿无法与当前实现通过稳定引用对应。

文案修正、等价图标替换和不改变视觉层级的缺陷修复无需重新审批。

### 7.2 API 审批

额外证据字段：

- 契约变更前后引用；
- 用例；
- Method 与 Path；
- 请求、响应、SSE payload 和错误模型；
- HTTP 状态码、权限、幂等与测试方案；
- 兼容性及迁移影响。

冻结 API 的 Method、Path、字段名称/类型/必填性、事件类型或顺序、状态码、错误码、权限、幂等语义发生任何不兼容变化，或新增接口时，必须重新审批。只修正文档错字且机器可读契约完全不变时无需重新审批。

### 7.3 Git 推送审批

额外证据字段：

- 目标远程仓库及 remote URL；
- 目标分支；
- 准确提交范围和最终 SHA；
- 提交内容摘要；
- 对应验收报告及结果；
- 推送原因；
- 是否会创建新远程分支。

每一次远程推送都必须单独审批。仓库、remote URL、目标分支、提交范围、最终 SHA、推送原因或测试结果任一变化，原批准立即失效。批准普通推送不构成 force push 批准；本项目仍禁止 force push 和直接推送 `main`。

## 8. 可验收词汇表

| 术语 | 本项目中的可验收定义 |
|---|---|
| 企业级界面 | 核心流程具备加载、空、错误、禁用状态；常用桌面和移动视口可用；键盘可完成核心流程；自动无障碍扫描无严重/致命问题；视觉基线已获用户批准 |
| 真实前后端联调 | 浏览器通过真实网络连接运行中的 FastAPI，后端使用真实 PostgreSQL、Redis、Chroma Adapter；仅模型与 Embedding 可使用确定性 Fake |
| 正确 HTTP 状态码 | 与冻结 API 契约逐接口列出的状态码完全一致；未写入契约的状态码不能靠实现自行解释 |
| 核心测试 | 第 4 节必过测试矩阵中的全部阻断项 |
| 全量回归 | 对最终集成 SHA 执行 `quality_gate.py all`，全部阻断项通过且无跳过 |
| 固定评测集 | 有版本、稳定 case ID、问题、应答标签、期望来源和变更历史的 25–30 条 RAG 样本 |
| 固定基线 | 与特定评测集、语料、分片配置、Embedding 和代码 SHA 绑定且经 QA 复核的指标快照 |
| 低置信度 | 归一化置信度低于配置阈值（默认 `0.65`），或无法提供支持关键结论的有效引用；实际阈值和算法版本必须进入运行追踪 |
| 高风险内容 | 涉及人身/设备安全、隐私数据、账号权限、不可逆数据修改或会触发外部实际动作的内容 |
| 关键工具 | 工具注册表中显式标记 `critical=true` 的工具；至少包括修改用户数据、提交审核结果或执行外部动作的工具 |
| 有上限重试 | 配置中存在明确最大次数、仅重试可恢复错误、使用可测试退避，且总耗时受请求超时限制 |
| 降级可用 | 预先定义的替代路径返回能力限制和安全状态；不得把无来源猜测、吞掉错误或伪造成功称为降级 |
| 健康检查通过 | 存活探针成功，且就绪探针确认服务可处理请求及必需依赖已就绪；仅进程存在不算通过 |
| 可重复运行 | 在锁定依赖和固定测试数据的干净环境中，连续两次执行唯一验收入口均得到相同通过结论 |
| 允许合并 | 最终集成 SHA 的全部阻断门通过、审批证据齐全、QA 明确记录“允许合并”，且此后候选内容未变化 |

若新文档使用“生产可用”“充分测试”“性能良好”“安全”“稳定”等无法直接测量的词，必须在同一文档中给出指标、阈值和验证方法，否则该要求视为未定义，不能作为完成依据。
